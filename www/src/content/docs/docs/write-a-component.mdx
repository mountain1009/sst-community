---
title: Write a Component
description: Build your own component from parts, with the same transform, nodes and linking as the built-in ones.
---

A component is a class that creates a few resources that belong together. You can write your own in your `sst.config.ts`, and use it the way you use the [built-in ones](/docs/components/).

You build it from **parts**: a list of the resources it creates. From that one list your component gets:

- A typed [`transform`](/docs/components/#transform) for each resource.
- `nodes`, with each resource it created.
- `existing`, to use a resource you already have in place of one it would create.
- Resource names made from the component's name.
- A check that it creates nothing outside the list.

The V5 components, like [`sst.aws.v5.Queue`](/docs/component/aws/v5/queue/), are built the same way.

---

## A component

Here's a component that creates a bucket for uploads, an optional second bucket for an audit trail, and a role for each team that reads from it.

```ts title="sst.config.ts"
const parts = {
  bucket: aws.s3.Bucket,
  // Only created when it's asked for
  audit: sst.optional(aws.s3.Bucket),
  // One per team
  reader: sst.many(aws.iam.Role),
};

interface UploadsArgs extends sst.ComponentArgs<typeof parts> {
  teams: string[];
  audit?: boolean;
}

class Uploads extends sst.component("acme:Uploads", parts) {
  constructor(name: string, args: UploadsArgs, opts?: $util.ComponentResourceOptions) {
    super(name, args, opts);

    this.part("bucket", { forceDestroy: true });
    if (args.audit) this.part("audit", {});
    for (const team of args.teams)
      this.part("reader", team, {
        assumeRolePolicy: aws.iam.assumeRolePolicyForPrincipal({
          Service: "lambda.amazonaws.com",
        }),
      });
  }

  get name() {
    return this.nodes.bucket.bucket;
  }
}
```

There are four things to it.

1. Declare the `parts`: a key for each resource, and its class.
2. Extend `sst.component(type, parts)`. The type is `<package>:<Name>`, and it's how your app's state knows the component.
3. Call `super(name, args, opts)` with the args as they are.
4. Create each resource with `this.part(key, args)`.

---

## Use it

It's used like any other component.

```ts title="sst.config.ts"
const uploads = new Uploads("Docs", {
  teams: ["design", "legal"],
});
```

This creates a bucket named `DocsBucket` and two roles, `DocsReaderDesign` and `DocsReaderLegal`. And whoever uses the component can change how each one is created.

---

#### Transform

An object is merged into the args the component sets, nested objects included. A function can change the args and the resource options.

```ts title="sst.config.ts"
new Uploads("Docs", {
  teams: ["design", "legal"],
  transform: {
    bucket: { tags: { team: "storage" } },
    reader: (args, opts, name, team) => {
      if (team === "legal") args.maxSessionDuration = 7200;
    },
  },
});
```

For a part there are several of, the function is also given which one it's looking at.

`$transform(Uploads, (args) => { ... })` works too. It runs before the component reads its args.

---

#### Existing

Pass a resource you already have, or the ID to look it up by, and the component uses it in place of creating one.

```ts title="sst.config.ts"
new Uploads("Docs", {
  teams: ["design"],
  existing: { bucket: "my-existing-bucket" },
});
```

---

#### Nodes

```ts title="sst.config.ts"
uploads.nodes.bucket;       // the aws.s3.Bucket
uploads.nodes.audit;        // undefined when it wasn't created
uploads.nodes.reader.legal; // by ID
```

:::note
A `transform` or `existing` key that isn't one of the parts is an error. The message lists the parts the component has.
:::

## Parts

A part's resource is named after the component and the part's key. So `Docs` and `bucket` give `DocsBucket`.

Every resource the component creates has to be a part. A resource created directly under the component that isn't in the list is an error. That's what keeps `transform` and `nodes` complete.

A part is declared with its class, or with one of these.

---

#### `sst.optional`

A part that's only sometimes created. Its entry in `nodes` may be `undefined`.

```ts
audit: sst.optional(aws.s3.Bucket)
```

---

#### `sst.many`

Several of one kind. Each is created with an ID, which is added to its name.

```ts
reader: sst.many(aws.iam.Role)
```

```ts
this.part("reader", "legal", { ... }); // DocsReaderLegal
```

An ID can be any string, like the route `GET /users/{id}`. To check whether one exists, use `id in this.nodes.reader`.

---

#### `sst.deferred`

A function that's built later, or not at all when it's given as an ARN. Create it with `sst.aws.functionPart`.

```ts
handler: sst.deferred(sst.aws.v5.Function)
```

```ts
sst.aws.functionPart(this, "handler", args.handler, { timeout: "30 seconds" });
```

Its entry in `nodes` is an `Output`. For a function per item, use `sst.many(sst.deferred(sst.aws.v5.Function))` and pass an ID.

---

#### `sst.named`

A part whose resource isn't named after its key. It wraps a class or one of the above.

```ts
audit: sst.named(sst.optional(aws.s3.Bucket), "Trail") // DocsTrail
```

The key is what's written in `transform`, `existing` and `nodes`. The name is how your deployed app knows the resource, so don't change it once it's deployed.

---

### Another component as a part

A part can be another component, like a [`sst.aws.v5.Function`](/docs/component/aws/v5/function/) or a component of your own.

```ts
const parts = {
  table: aws.dynamodb.Table,
  cleanup: sst.aws.v5.CronV2,
};
```

---

### Create a part later

Create a part inside an `.apply()` when whether it exists depends on something that's only known on deploy, like another component's output. Declare it with `sst.optional` or `sst.many`. It's added to `nodes` when it's created.

Do this only when an arg can't decide it.

---

### Resources something else creates

Sometimes another function creates resources under your component, like a DNS adapter creating records. Give it `this.delegateOpts()` as its options.

```ts
dns.createAlias(name, record, this.delegateOpts());
```

These aren't parts. They're configured through whatever creates them, so they have no `transform` and aren't in `nodes`.

---

## Args

Your args extend `sst.ComponentArgs<typeof parts>`, which adds `transform` and `existing`.

---

#### Plain values decide what's created

If whether a part exists depends on an arg, take that arg as a plain value and not as an [`Output`](/docs/components/#outputs). The component has to know before it creates anything.

```ts
interface UploadsArgs extends sst.ComponentArgs<typeof parts> {
  // Decides how many roles there are
  teams: string[];
  // Doesn't, so it can be an output
  retention?: $util.Input<number>;
}
```

The same goes for a list with a part per item, and for the field each part is named after. This is what lets `nodes` hold resources and not outputs of resources.

---

#### Switch a part off

Give a part someone can do without an arg of its own, like `audit: false`. A `transform` changes a part; it doesn't remove one.

---

#### Reference what's deployed

A static `get` is one line with `existing`.

```ts
static get(name: string, bucketName: string, opts?: $util.ComponentResourceOptions) {
  return new Uploads(name, { teams: [], existing: { bucket: bucketName } }, opts);
}
```

In the constructor, `this.part()` returns the existing resource in place of creating one. When your component has more to do for a resource it didn't create, `this.existingPart("bucket")` returns it, or `undefined`.

## Link it

Define `link()` to make your component [linkable](/docs/linking/).

```ts title="sst.config.ts"
class Uploads extends sst.component("acme:Uploads", parts) {
  // ...

  link() {
    return {
      properties: { name: this.name },
      include: [
        sst.aws.permission({
          actions: ["s3:GetObject"],
          resources: [$interpolate`${this.nodes.bucket.arn}/*`],
        }),
      ],
    };
  }
}
```

The `properties` are readable at runtime as `Resource.Docs.name`. And `include` is what a function that links it is granted: AWS permissions with `sst.aws.permission()`, Cloudflare bindings with `sst.cloudflare.binding()`, and environment variables with `sst.env()`.

```ts title="sst.config.ts"
new sst.aws.v5.Function("Api", {
  handler: "src/api.handler",
  link: [uploads],
});
```

---

## Dev mode

If your component runs something locally in `sst dev` and isn't deployed, say so in one place in the constructor. Call `this.runsLocally()` and return before creating the parts that aren't deployed there.

```ts
if ($dev) {
  this.runsLocally();
  return;
}
```

Reading `nodes` then explains why the resource isn't there. A part you create all the same, like the role the local process runs as, is in `nodes` as usual.

---

## Names in your provider

SST gives the resources of the types its own components use a name made from your app, stage and the resource's name. For another type, say which field holds the name.

```ts title="sst.config.ts"
sst.Component.naming("aws:athena/workgroup:Workgroup", { field: "name", max: 128 });
```

Or pass `false` to leave the name to the provider. A resource that's looked up keeps the name it has.

---

## Rename a part

A part's key is in the name of its resource. So a new key is a new resource, and the old one is removed.

To change a key and keep what's deployed, declare the part with the name it had.

```ts del={2} ins={3}
const parts = {
  bucket: aws.s3.Bucket,
  files: sst.named(aws.s3.Bucket, "Bucket"),
};
```

Or give the resource its new name, and say where it was.

```ts title="sst.config.ts"
sst.takeover(Uploads, {
  moved: { files: "bucket" },
});
```

The same call lets a new component take over from another one. Give it the other component's type in `from`, and keep the name you gave the component.

## Test it

You can test your component without deploying it. Put it in a file of its own and export it.

```ts title="infra/uploads.ts"
const parts = {
  bucket: aws.s3.Bucket,
  // ...
};

export class Uploads extends sst.component("acme:Uploads", parts) {
  // ...
}
```

Then `mock` stands in for what deploys your app. It gives your test everything your `sst.config.ts` has, like `sst`, `aws` and `$app`, and records each resource your component creates.

```ts title="uploads.test.ts"
import { beforeEach, expect, test } from "vitest";
import { mock } from "./.sst/platform/src/testing";

const app = await mock();
const { Uploads } = await import("./infra/uploads");

beforeEach(() => app.reset());

test("creates a role for each team", async () => {
  new Uploads("Docs", { teams: ["design", "legal"] });
  await app.settle();

  expect(app.resources.map((r) => r.name).sort()).toEqual([
    "Docs",
    "DocsBucket",
    "DocsReaderDesign",
    "DocsReaderLegal",
  ]);
});
```

Nothing is deployed, and no provider is called. This works with [Vitest](https://vitest.dev) and with `bun test`.

:::note
Call `mock` before your component's file is loaded. That file reads `sst` and `aws` as it loads, which is why it's imported with `await import`.
:::

The `.sst/platform` directory is created by `sst install`, so run that first in a fresh checkout.

---

#### What you get

- `app.resources` has each resource that was created, with its `type`, `name`, `parent`, the `inputs` it was given and its `options`.
- `app.settle()` waits until everything has been created.
- `app.resolve(value)` reads an `Output`.
- `app.reset()` empties the list, so each test sees its own resources.

```ts title="uploads.test.ts"
test("turns on force destroy", async () => {
  const uploads = new Uploads("Docs", { teams: [] });
  await app.settle();

  const bucket = app.resources.find((r) => r.name === "DocsBucket")!;
  expect(bucket.inputs.forceDestroy).toBe(true);
  expect(await app.resolve(uploads.name)).toMatch(/^app-test-docsbucket-/);
});
```

---

#### What a resource returns

A resource comes back with the inputs it was given, an ID of `<name>_id`, and an ARN made from its name. If your component reads another output, say what it is with `state`. And `call` does the same for a function like `aws.getRegion`.

```ts title="uploads.test.ts"
const app = await mock({
  state: (args) =>
    args.type === "aws:s3/bucket:Bucket"
      ? { bucketRegionalDomainName: `${args.name}.s3.amazonaws.com` }
      : {},
  call: (args) =>
    args.token === "aws:index/getRegion:getRegion"
      ? { name: "eu-west-1", region: "eu-west-1" }
      : undefined,
});
```

You can also pass the `app` name and the `stage`, which are `app` and `test` by default. To test what your component does in `sst dev`, pass `dev: true`.

---

#### Check a change before you deploy it

A component that's deployed can lose a resource when you change it. A renamed part is a new resource, and the old one is removed.

To catch that, save what your component creates when you deploy it.

```ts title="uploads.test.ts"
new Uploads("Docs", { teams: ["design"] });
await app.settle();
fs.writeFileSync("uploads.deployed.json", JSON.stringify(app.graph()));
```

Then check your changes against it.

```ts title="uploads.test.ts"
test("keeps what's deployed", async () => {
  const deployed = JSON.parse(fs.readFileSync("uploads.deployed.json", "utf8"));

  new Uploads("Docs", { teams: ["design"] });
  await app.settle();

  expect(app.takeover(deployed)).toEqual({
    unclaimed: [],
    changed: [],
    unordered: [],
  });
});
```

Here `unclaimed` are the resources a deploy would remove. And `changed` are the ones it would update, with the inputs that are different. A part that's [renamed](#rename-a-part) with `sst.named` or `sst.takeover` passes this.

A function is also in `changed` when what its code is built from is different: its handler, its runtime, or its links. A function's links are written into its code, so they aren't in the inputs of anything it creates.

And `unordered` are the resources that were removed in order before, and aren't now. Resources are removed in the reverse of the order they depend on each other. So if a database no longer depends on its subnet group, the two are removed in any order, and AWS refuses to delete a subnet group that's still in use.

## Share it

A component can be published as a package and used in any app on version 5.

In a package, import what the component uses: the components from `sst/components`, and each provider from its package. When an app runs the component, both are the app's own, so the package uses the same SST and the same providers as the app. `sst/components` has what SST's components share, and `sst/components/aws`, `sst/components/cloudflare` and `sst/components/vercel` have the components of each provider. Together they're what the `sst` global is.

```ts title="src/index.ts"
import { component, type ComponentArgs, type LinkDefinition } from "sst/components";
import type { ComponentResourceOptions } from "@pulumi/pulumi";
import * as aws from "@pulumi/aws";
import * as cloudflare from "@pulumi/cloudflare";

const parts = {
  identity: aws.ses.DomainIdentity,
  verification: cloudflare.DnsRecord,
};

export interface EmailDomainArgs extends ComponentArgs<typeof parts> {
  domain: string;
  zoneId: string;
}

export class EmailDomain extends component("acme:EmailDomain", parts) {
  constructor(name: string, args: EmailDomainArgs, opts?: ComponentResourceOptions) {
    super(name, args, opts);

    const identity = this.part("identity", { domain: args.domain });
    this.part("verification", {
      zoneId: args.zoneId,
      name: `_amazonses.${args.domain}`,
      type: "TXT",
      content: identity.verificationToken,
      ttl: 60,
    });
  }

  link(): LinkDefinition {
    return { properties: { domain: this.nodes.identity.domain } };
  }
}
```

---

#### Set it up

The package's repo installs `sst`, Pulumi and the providers the component uses as dev dependencies. It needs no `sst.config.ts`.

```bash
npm install -D sst@npm:@sst-community/sst@^5.0.0-0 @pulumi/pulumi @pulumi/aws @pulumi/cloudflare typescript
```

`sst/components`, `sst/components/aws` and the other groups come from it, with their types, and `sst/testing` too. A component that uses SST's components of a provider, like `sst/components/aws`, also needs the providers that group loads. For `sst/components/aws` they're `@pulumi/aws`, `@pulumi/command`, `@pulumi/docker-build`, `@pulumi/random` and `@pulumi/tls`. `node_modules/sst/platform/package.json` lists each group's under `groups`.

`tsc` compiles the component to JavaScript and a `.d.ts`.

```json title="tsconfig.json"
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,
    "skipLibCheck": true,
    "declaration": true,
    "outDir": "dist",
    "rootDir": "src"
  },
  "include": ["src"]
}
```

Say which versions of SST and which providers the component works with, as peer dependencies.

```json title="package.json"
{
  "name": "@acme/email-domain",
  "type": "module",
  "main": "dist/index.js",
  "types": "dist/index.d.ts",
  "files": ["dist"],
  "peerDependencies": {
    "sst": ">=5.0.0-0",
    "@pulumi/aws": "^7",
    "@pulumi/cloudflare": "^6"
  },
  "peerDependenciesMeta": {
    "@pulumi/aws": { "optional": true },
    "@pulumi/cloudflare": { "optional": true }
  }
}
```

An app that installs the package gets its components checked against these when it deploys. If the app doesn't have one of the providers, the deploy stops and says to add it with `sst add`. The same happens if the app's SST or one of its providers is a version outside the range. The providers are optional so that a package manager doesn't install another copy of each in the app, which has its own. `>=5.0.0-0` includes the prereleases of version 5.

When an app runs the component, its `sst/components` and its providers are the app's own, not the ones the package's repo installed.

---

#### Test the package

Test the component with `mock()` from `sst/testing`, as in [Test it](#test-it). It works in vitest, `bun test` and `node --test`, with nothing to set up.

```ts title="test/email-domain.test.ts"
import { expect, test } from "vitest";
import { mock } from "sst/testing";

const app = await mock();
const { EmailDomain } = await import("../src/index");

test("verifies the domain in Cloudflare", async () => {
  app.reset();
  new EmailDomain("Mail", { domain: "example.com", zoneId: "Z1" });
  await app.settle();

  const record = app.resources.find((r) => r.type === "cloudflare:index/dnsRecord:DnsRecord");
  expect(record?.inputs.name).toBe("_amazonses.example.com");
});
```

`mock()` gives the test `sst` with the components of each provider whose packages are installed, like `sst.aws`. Using one that isn't fails, and says what to install.

---

#### Use it

In an app, install the package, add the providers it needs, and import it in `run()`.

```ts title="sst.config.ts"
const { EmailDomain } = await import("@acme/email-domain");

const email = new EmailDomain("Mail", {
  domain: "example.com",
  zoneId: "023e105f4ecef8ad9ca31a8372d0c353",
  transform: { verification: { ttl: 300 } },
});
```

An app without a `package.json` lists the package in its config instead, under `packages`. A command like `sst deploy` installs it with the providers.

```ts title="sst.config.ts" {6}
app(input) {
  return {
    name: "my-app",
    home: "aws",
    providers: { cloudflare: "6.15.0" },
    packages: { "@acme/email-domain": "1.2.0" },
  };
},
```

For TypeScript to read the package's types, the app's `tsconfig.json` extends `.sst/tsconfig.json`, which `sst install` writes. It says where the app's SST and providers are, in `.sst/platform`.

```json title="tsconfig.json" {2}
{
  "extends": "./.sst/tsconfig.json",
  "compilerOptions": {
    // ...
  }
}
```

:::note
`paths` in your own `tsconfig.json` replace the ones it extends. If you have some, add the entries from `.sst/tsconfig.json` to yours. `sst install` changes them when you add a provider.
:::

If the app's tests load the package, give vitest the same, so a test uses the app's SST and providers, as a deploy does.

```ts title="vitest.config.ts"
import { defineConfig } from "vitest/config";
import { alias } from "./.sst/platform/src/testing/vitest";

export default defineConfig({ resolve: { alias } });
```

A component can also be written with the `sst` and provider globals, as in your app, and published as TypeScript. Then the app needs no change to its `tsconfig.json`, but nothing in the package says what it depends on.
